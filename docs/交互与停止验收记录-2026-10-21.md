## 连接与多网卡

- `zs-support connect` 在终端先选择 L1/1W、L2、M1，不自动尝试其他产品账号。
- 两板身份和版本并行查询，只读本体 `/userdata/config/device.json` 的 SN/tag/type；连接时不扫描数据路径或查询 ROS。
- 该机实测显式连接 0.92 秒；PTY 产品选择完成后各次约 0.74～2.57 秒，成功样本的网络时延不同。不能视为所有网络的固定耗时。
- 本体使用 `192.168.234.1`，NX 使用 `192.168.168.100`。现场同时有公司无线 `wlp0s20f3` 和机器人无线 `wlx90de80def799`，另有 VPN/Meta。
- 初始内网168路由指向 Meta，SSH BindInterface 仍无法连通 NX。用户在本机手动添加 `sudo ip route add 192.168.168.0/24 via 192.168.234.1 dev wlx90de80def799` 后连通。代码只做网卡选择和路由诊断，不执行 sudo 或修改系统路由。
- 自动优先本地直连的 AP 入口，支持 `connect --interface <实际网卡>`；SSH 与 rsync 使用一致的网卡参数。明确绑定不能代替有效的系统路由。

## 停止问题与修复

原用户会话 `11bd519dfbf842b290b24dcf13353f5d` 第一次停止已完成；重复启动被拒的 `24006959e2c443caa4f67937f6f18cc5` 却被保留为 unknown，第二次 stop 误选该记录并报错。

本版将明确的重复启动拒绝记作 failed；网络超时或未知异常保留待确认状态。对已超过启动超时窗口、确认没有远端会话标识的旧记录做兼容核验，不删除历史文件。stop 只选择当前设备仍活动的任务，无活动任务时成功返回；指定已完成会话重复停止同样返回已完成。

真机回归另发现并修复：

1. 大场景启动请求超过管道缓冲时，Python 3.10 的 communicate 短超时重试可能不再发送剩余输入，导致远端等待 EOF。改为私有临时文件提供完整输入；新增延迟读入 1 MiB 请求的真实进程回归。
2. 停止成功后的会话也含 scenes 字段，被输出层误当作场景预览，导致显示时报 TypeError。按会话标识分流，新增结果渲染回归。
3. 未发布话题可等待后续发布，但正常停止而消息数为零时不能视为有效 Bag。保留异常数据标记并明确提示“录制已停止，但未收到任何话题消息”，避免混淆为停止信号失败。
